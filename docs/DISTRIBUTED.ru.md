# Распределённая обработка событий безопасности

> 🌐 [English](DISTRIBUTED.md) | [Українською](DISTRIBUTED.uk.md)

Один бинарник ArxSentinel. Любое число узлов. Собирайте события безопасности
там, куда приходит трафик, скорируйте там, где есть вычислительные ресурсы,
применяйте меры там, где это больнее всего для атакующего — через сквозно
зашифрованную, взаимно аутентифицированную event-сетку, встроенную прямо в
движок. Без Redis, без Kafka, без log shipper'а, без VPN, без центрального
сервера.

Это руководство для операторов: что такое распределённый pipeline, как
устроены его части, и пять типовых инфраструктур, которые можно скопировать
уже сегодня. Каждая топология здесь проверяется в CI реальными
мультиконтейнерными тестами
([`tests/integration/distributed-ncs/`](../tests/integration/distributed-ncs/README.md)) —
диаграммы не «планы на будущее».

## Идея за 60 секунд

В ArxSentinel всегда была внутренняя шина событий — **Named Channel Switch
(NCS)**: один pipeline пишет события в именованную очередь, другой pipeline
(или executor) читает их обратно. До сих пор очередь жила внутри одного
процесса.

**Distributed NCS** протягивает ту же очередь через сеть. Добавьте блок
`queue: {type: transport}` к sink'у или source — и бэкендом именованной
очереди становится QUIC-соединение с другим узлом. Та же форма конфига, та же
семантика pipeline, но два конца теперь на разных машинах:

```
      УЗЕЛ A                                       УЗЕЛ B
 ┌────────────────┐                          ┌────────────────┐
 │ pipeline        │   очередь "edge-raw"     │ pipeline        │
 │   sink ─────────┼── QUIC / TLS 1.3 ──────▶│   source        │
 │                 │    Ed25519 + TOFU        │                 │
 └────────────────┘                          └────────────────┘
```

Остальной движок — парсеры, детекторы, скорер, whitelist, executor'ы — не
знает и не хочет знать, что случился сетевой хоп. Именно это правило дизайна
превращает каждую топологию ниже в чистое упражнение по конфигурации.

## Три роли, один бинарник

Никаких специальных сборок «агент», «сервер» или «менеджер» не существует.
Каждый узел запускает один и тот же бинарник с одним форматом конфига; его
**роль** — просто набор включённых частей pipeline:

| Роль | Что делает | Ключевой конфиг |
|------|-----------|-----------------|
| **Коллектор** | Читает/принимает логи, парсит, пробрасывает **нескорированные** записи дальше. Дёшево: без tracker-состояния, без работы детекторов. Спокойно живёт на Raspberry Pi или VPS со 128 MB. | `raw_forward: true` + transport-sink (`mode: send`) |
| **Детектор** | Принимает записи от любого числа коллекторов, прогоняет полную цепочку (8 поведенческих детекторов, WAF-правила, whitelist, скоринг), пробрасывает **скорированные вердикты** дальше. Одна точка тюнинга порогов для всего флота. | transport-source (`mode: raw`, queue `mode: recv`) + transport-sink для вердиктов |
| **Респондер** | Принимает скорированные вердикты и применяет меры: nginx blocklist, MikroTik address-list, Cloudflare WAF или собственный exec+JSON executor. Живёт рядом с точкой применения — учётные данные не покидают этот узел. | `executors:` с transport-источником (queue `mode: recv`) |

Роли свободно комбинируются: узел может детектировать **и** отвечать,
собирать **и** детектировать локально, пробрасывая только высокоуровневые
вердикты, и так далее. Деплой на 2 узла и деплой на 20 узлов строятся из
одних и тех же трёх кубиков.

## Что летит по сети

Два формата полезной нагрузки, выбираются на каждую очередь:

**Сырые записи** (`raw_forward: true` + `format: raw-line` на отправляющем
sink'е, `mode: raw` на принимающем source). Коллектор парсит строку в
структурированную запись (IP, метод, путь, статус, UA, timestamp), но **не**
скорирует её. Узел-детектор скорирует её ровно так, как если бы строка была
прочитана из локального файла. Применяйте, когда нужна централизованная
детекция с одной общей политикой скоринга и общим per-IP состоянием.

**Скорированные вердикты** (payload `sentinel-threat` по умолчанию — без
дополнительных флагов). Полный ThreatEvent: IP, score, уровень, какие
детекторы сработали, человекочитаемая причина. Применяйте, когда детекция уже
случилась и нужно лишь доставить вердикт туда, где живёт enforcement (или
хранилище, или SIEM).

Типичный деплой использует оба: сырые записи текут внутрь с периметра,
скорированные вердикты — наружу к респондерам.

## Модель безопасности транспорта

Сетка построена на `arx-core/pkg/transport`:

- **QUIC поверх UDP** — один порт на узел (по умолчанию `4097`),
  мультиплексированные стримы, автоматический reconnect с экспоненциальным
  backoff. Переживает нестабильные линки.
- **Всегда TLS 1.3** — plaintext-режима, который можно было бы случайно
  включить, не существует.
- **Ed25519-идентичность узла** — каждый узел генерирует ключевую пару при
  первом старте (`transport.identity`). Без CA, без календаря истечения
  сертификатов.
- **Общесетевой секрет допуска** (`transport.pairing_secret`) — реальный
  барьер против чужаков: неизвестный узел должен доказать знание этого
  общего, переданного вне протокола секрета, прежде чем ему вообще начнут
  доверять. Без него один только TOFU отвечает лишь на вопрос «тот же ли
  ключ, что вчера» — но ничего не говорит о том, кто вообще разрешил этому
  ключу присоединиться. Одно и то же значение — на каждом узле сетки.
- **TOFU-пиннинг + самовосстанавливающаяся ротация** (`transport.known_nodes`)
  — после допуска fingerprint пира фиксируется; отдельный, независимый
  секрет затем автоматически ротируется после каждой сессии (без действий
  оператора) — так устаревшая утёкшая копия конфига со временем перестаёт
  совпадать. Для ещё более строгой гарантии поверх общесетевого секрета —
  закрепите ожидаемый fingerprint заранее в конфиге
  (`peers[].fingerprint: "sha256:..."`) — проверяется раньше, чем секрет
  допуска или TOFU вообще вступают в дело.
- **Взаимная аутентификация** — обе стороны доказывают владение ключом через
  подписанный challenge до того, как потечёт хоть одно событие. Чужак,
  нашедший ваш UDP-порт без общесетевого `pairing_secret`, не получает
  ничего.

Чем сетка **не** является: брокером сообщений с гарантиями доставки. Если
пир недоступен, кадры для него отбрасываются и считаются (видно в логах и
drop-счётчиках) — та же семантика «потеря при переполнении», что и у
in-memory очереди. Для буферизации с переживанием рестарта — комбинируйте с
bbolt-очередью на принимающей стороне
(см. `arx-core/pkg/transport/OPERATIONS.md`).

## Поверхность конфигурации

Всё живёт в том же YAML, который вы уже знаете. Полный справочник:
[`cookbook/config.reference.yaml`](../cookbook/config.reference.yaml).

```yaml
# 1. Включаем сетку на каждом участвующем узле — pairing_secret одинаков
#    везде, включая узлы без собственных peers: (принимающий-только узел
#    всё равно сверяет свой секрет со входящими подключениями).
transport:
  enabled: true
  identity: /etc/arxsentinel/node.key        # генерируется при первом старте
  known_nodes: /etc/arxsentinel/known-nodes  # хранилище TOFU-пинов + ротируемый секрет
  listen: "0.0.0.0:4097"                     # QUIC/UDP
  pairing_secret: "..."                      # общесетевой, передан вне протокола
  peers:                                     # только исходящие цели набора;
    - host: "detector.example.net:4097"      # входящие соединения принимаются
      fingerprint: ""                        # и TOFU-пинятся в любом случае

# 2. Отправляющая сторона — любой sentinel-threat sink может указывать на пира
outputs:
  - type: sentinel-threat
    name: edge-raw            # имя очереди — должно точно совпадать с приёмником
    format: raw-line          # только для сырых записей; убрать для вердиктов
    queue:
      type: transport
      mode: send
      peer: "detector.example.net:4097"

# 3. Принимающая сторона — sentinel source или источник executor'а
inputs:
  - type: sentinel
    addr: ncs://edge-raw      # то же имя очереди
    mode: raw                 # декодировать сырые записи; убрать для вердиктов
    queue:
      type: transport
      mode: recv
```

`arxsentinel validate --config ...` статически проверяет проводку на каждом
узле: transport-очереди требуют `transport.enabled`, send-очереди требуют
известного пира, а кросс-нодовые очереди освобождены от локальных проверок
reader/writer.

## Сравнение с альтернативами

Распределённая защита на основе логов — не новая концепция: модель
agent/LAPI/bouncer у CrowdSec и модель agent/manager у Wazuh существуют и
работают. Отличается здесь *форма* архитектуры:

| | CrowdSec | Wazuh / OSSEC | ArxSentinel |
|---|---|---|---|
| **Топология** | Hub-and-spoke: центральный LAPI (HTTP REST + обязательная БД) | Agent → manager (полная платформа: manager, indexer, dashboard) | Симметричный peer mesh — без центрального сервера, без БД |
| **Компоненты** | Агент + LAPI + отдельные бинарники-баунсеры на каждую точку enforcement | Manager-стек + агенты | Один бинарник ~12 MB; роль (коллектор / детектор / респондер) — это просто YAML |
| **Что летает по сети** | Только алерты и решения — для централизации детекции сырые логи нужно везти отдельным shipper'ом (syslog, vector) | События агентов на manager | Сырые распарсенные записи **и** скорированные вердикты — через один встроенный транспорт |
| **Модель доставки** | Pull: баунсеры опрашивают LAPI за решениями | Push: agent → manager | Push по QUIC-mesh, автоматический redial |
| **Аутентификация** | API-ключи / TLS-сертификаты | Pre-shared keys | Ed25519-идентичность узла + TOFU-пиннинг, взаимная — как SSH |
| **Footprint на узел** | Агент + баунсер(ы); LAPI-узлу нужна БД | Manager измеряется гигабайтами RAM | ~12 MB статический бинарник везде, включая arm/v7 и riscv64 |

Обе альтернативы — крепкие проекты со своими сильными сторонами (в
частности, у community-блоклистов CrowdSec здесь эквивалента нет).
Утверждение этого руководства уже и точнее: **ни один другой инструмент в
этом классе не поставляет peer-to-peer сетку событий безопасности внутри
самого движка** — один и тот же бинарник на каждом узле, без иерархии
агент-сервер, без отдельных компонентов enforcement, и с пробросом сырых
записей на удалённый детектор через собственный транспорт движка — чего не
предлагает ни один из перечисленных.

## Топология 1 — Два узла: собираем здесь, детектируем там

Минимальный распределённый сетап и базовый паттерн для всего остального.
Веб-сервер держит крошечный коллектор рядом со своими логами; вся логика
детекции, тюнинг и состояние живут на второй машине.

```
   веб-сервер (VPS, 12 MB на коллектор)             машина детекции
 ┌──────────────────────────────┐            ┌──────────────────────────────┐
 │ nginx → access.log            │            │                                │
 │   │ tail                      │   QUIC     │  sentinel source (mode: raw)   │
 │   ▼                           │  ───────▶  │    │                           │
 │ pipeline коллектора           │ "edge-raw" │    ▼                           │
 │  только парсинг — raw_forward │            │  8 детекторов · WAF · whitelist│
 │  sink: transport, mode: send  │            │  скорер → threats.log / баны   │
 └──────────────────────────────┘            └──────────────────────────────┘
```

**Когда**: не хотите CPU/состояние детекторов на веб-сервере; хотите тюнить
скоринг в одном месте; веб-машина должна оставаться минимальной.

**Рецепт**: [`cookbook/distributed-ncs/`](../cookbook/distributed-ncs/README.md)
(`collector.yaml` + `detector.yaml`, полный walkthrough внутри).

## Топология 2 — Edge-флот: много коллекторов, один мозг

Агрегация: любое число коллекторов пробрасывает на **одно и то же имя
очереди**; единственная регистрация на детекторе принимает всех. Одна
политика скоринга, один whitelist, одно общее per-IP состояние — атакующий,
прощупывающий три ваших сервиса, накапливает один суммарный score и
пересекает порог бана раньше, чем его поймал бы любой сервис поодиночке.

```
 ┌────────────────┐
 │ nginx edge      │──┐
 └────────────────┘  │
 ┌────────────────┐  │  очередь "edge-raw"  ┌──────────────┐   очередь        ┌──────────────┐
 │ API gateway     │──┼───────────────────▶│   детектор    │─────────────────▶│  респондер    │
 └────────────────┘  │  (одно имя со всех  │ полная цепочка│ "scored-events"  │ nginx executor │
 ┌────────────────┐  │   коллекторов)      │ общее состояние│                 │ blocklist-файл │
 │ auth service    │──┘                     └──────────────┘                  └──────────────┘
 └────────────────┘
```

**Когда**: разнородные источники (веб-слой + API + auth), корреляция атак
между сервисами, «добавить коллектор» должно быть 30 строками YAML, а не
инфраструктурным проектом.

**Рецепт**: [`cookbook/distributed-ncs/aggregation/`](../cookbook/distributed-ncs/aggregation/README.md).
**CI-доказательство**: `docker-compose.aggregation.yml` — 5 реальных
контейнеров, на каждом PR.

## Топология 3 — Смешанная маршрутизация: разные источники — разные меры

Один процесс-детектор, несколько pipeline — каждый принимает трафик своего
источника и пробрасывает вердикты своему респондеру. Атаки на веб-слой
банятся на веб-уровне; атаки на auth/сеть — на роутере. Решение о маршруте —
это то, через какой pipeline трафик вошёл; принимается на этапе конфига, ноль
per-event логики маршрутизации.

```
 ┌────────────────┐  "edge-web"         ┌──────────────────┐  "scored-web"     ┌─────────────────┐
 │ collector-web  │────────────────────▶│ pipeline "web"   │──────────────────▶│ nginx-респондер │
 └────────────────┘                     │                  │                   │ blocklist-файл  │
 ┌────────────────┐  "edge-auth"        │     детектор     │                   └─────────────────┘
 │ collector-auth │────────────────────▶│ pipeline "auth"  │  "scored-auth"    ┌──────────────┐
 └────────────────┘                     │                  │──────────────────▶│ MikroTik     │
                                        └──────────────────┘                   │ address-list │
                                                                               └──────────────┘
```

**Когда**: разным классам трафика нужны разные механизмы enforcement или
разные политики TTL/severity, но детекция должна остаться на одной машине.

**Рецепт**: [`cookbook/distributed-ncs/mixed-routing/`](../cookbook/distributed-ncs/mixed-routing/README.md).
**CI-доказательство**: `docker-compose.mixed-routing.yml` — включает реальный
мок RouterOS API и кросс-проверки, что вердикты не «протекают» между
маршрутами.

## Топология 4 — Хоумлаб: Pi-коллекторы, NAS-мозг, бан на роутере

Весь флот стоит вам ~40 MB RAM суммарно. Коллекторы запускаются везде, где
пишется лог — включая arm/v7 и riscv64-платы. Мозг живёт на том, что всегда
включено (NAS, мини-ПК). Enforcement происходит на вашем MikroTik —
атакующие отбрасываются на границе сети, не дотянувшись ни до одного сервиса.

```
 ┌────────────────────────────┐
 │ Raspberry Pi · логи прокси │──┐
 └────────────────────────────┘  │              ┌──────────────────────┐               ┌─────────────────────┐
 ┌────────────────────────────┐  │  "edge-raw"  │    NAS / мини-ПК     │  "scored"     │ MikroTik executor   │
 │ VPS · публичный веб        │──┼─────────────▶│ детектор: 8 цепочек  │──────────────▶│ (тоже на NAS —      │
 └────────────────────────────┘  │              │ + WAF + whitelist    │               │ креды RouterOS      │
 ┌────────────────────────────┐  │              └──────────────────────┘               │ не покидают дом)    │
 │ NAS · локальные сервисы    │──┘                                                     └─────────────────────┘
 └────────────────────────────┘                                                                   ▼
                                                                                      /ip/firewall/address-list
                                                                                          → drop на роутере
```

**Когда**: несколько машин, один оператор и ноль желания держать дома Kafka.
Транспорт сам себе VPN — плечо от VPS уже зашифровано TLS 1.3 и запинено,
так что публичному коллектору не нужен туннель домой. Из интернета должен
быть доступен только UDP-порт детектора (один порт-форвард на роутере).

**С чего начать**: рецепт Топологии 2 с одним коллектором на машину; замените
executor респондера на `type: mikrotik`
(конфиг executor'а — в [`cookbook/mikrotik/`](../cookbook/mikrotik/)).

## Топология 5 — Корпоративная: edge-детекция + поток в SIEM

Вынесите детекцию туда, куда приходит трафик (филиалы, edge-PoP,
DMZ-сегменты), и отправляйте в корпоративный стек **структурированные,
предварительно скорированные события** — а не гигабайты сырых логов. Каждый
узел умеет выдавать оба формата одновременно:

- **Сырые нормализованные записи** — каждый распарсенный запрос как
  структурированный JSON (`format: raw-line` или локальный `json`
  file/stdout-sink): полный поток для threat hunting, форензики и моделей,
  которым нужно всё.
- **Скорированные вердикты** — только то, что пересекло порог, со score,
  списком детекторов и причиной: alert-grade поток, который ваш SOC реально
  читает, при доле объёма инжеста.

```
 ┌────────────────────┐  "edge-*" · QUIC            ┌──────────────────────────┐             ┌──────────────────┐
 │ коллектор · филиал │────────────────────────────▶│    кластер детекции      │  exec+JSON  │ SIEM / data lake │
 └────────────────────┘                             │   (per-site или центр)   │────────────▶│ Splunk · Elastic │
                                                    │ сырой JSON + score ────▶ │             │ QRadar · любой   │
 ┌────────────────────┐                             │                          │             └──────────────────┘
 │ коллектор · DMZ    │────────────────────────────▶│ скорированные вердикты ▶ │             ┌───────────────────┐
 └────────────────────┘                             │                          │────────────▶│ enforcement       │
                                                    └──────────────────────────┘  QUIC-сетка │ CF WAF · MikroTik │
                                                                                             │ nginx · exec+JSON │
                                                                                             └───────────────────┘
```

Ключевые свойства для корпоративной оценки:

- **Контроль стоимости инжеста.** Префильтрация на edge означает, что счёт за
  SIEM определяется *угрозами*, а не *трафиком*. Переключите один sink на
  `raw-line`, когда расследованию нужен полный поток — per pipeline, per site.
- **Без входящих дырок.** Коллекторы соединяются **наружу** к детектору;
  файрволам филиалов не нужно ни одного входящего правила. Учётные данные
  enforcement (токены Cloudflare, пароли RouterOS) живут только на
  узлах-респондерах.
- **Единый агент.** Один и тот же статический бинарник ~12 MB на каждом
  узле — amd64, arm64, arm/v7, riscv64, i386, Linux и FreeBSD — один пакет
  для сертификации, один формат конфига для ревью.
- **Дружелюбно к аудиту.** `arxsentinel validate` доказывает проводку
  офлайн; каждая топология этого руководства прогоняется CI на реальных
  контейнерах при каждом merge.

**Пути в SIEM уже сегодня**: `exec+JSON` sink (любой скрипт/бинарник —
HEC-аплоадер, Kafka-продьюсер, S3-writer), `file` sink в формате JSON
(подхватывается любым существующим форвардером), `stdout` JSON (контейнерные
лог-пайплайны). Нативные sink'и Splunk HEC / Loki / Datadog — в
[роадмапе](https://mr-addams.github.io/arxsentinel/ru.html#roadmap).

## Эксплуатация

- **Порядок запуска**: для корректности не важен — дозвон повторяется с
  backoff (1s → 30s, с джиттером). Запуск приёмников первыми лишь экономит
  первый backoff-удар.
- **Имена очередей должны совпадать точно** на обоих концах (`name:` на
  sink'е, `ncs://<имя>` на source). Несовпадение — не ошибка старта (имя
  становится значимым, только когда оба узла подняты) — оно проявляется как
  растущий drop-счётчик и rate-limited WARN на приёмнике. Процедура
  диагностики: `arx-core/pkg/transport/OPERATIONS.md` §4.
- **Файрвол**: один UDP-порт на узел (по умолчанию `4097`), только в
  направлении набора коллектор→детектор / детектор→респондер.
- **Ротация ключа / компрометация узла**: удалите строку узла из
  `known_nodes` каждого пира, удалите файл `identity` узла, перезапустите —
  свежая ключевая пара сгенерируется и перепинится при следующем контакте
  (ей снова придётся пройти гейт `pairing_secret`, как любому новому узлу).
  Заранее прописанные fingerprints в конфиге тоже нужно обновить.
- **Ротация секрета допуска — автоматическая** — никаких действий оператора
  в штатном режиме не требуется, она ротируется сама после каждой успешной
  сессии. Если вы подозреваете утечку самого значения `pairing_secret` (не
  идентичности одного узла, а общесетевого секрета) — ротируйте его явно:
  сгенерируйте новый, обновите на каждом узле, перезапустите все вместе
  (узел на старом значении не пройдёт допуск с узлами уже на новом).
- **Семантика отказов**: недоступный пир отбрасывает (и считает) кадры,
  отправленные ему; переподключение автоматическое. Состояние детекции живёт
  на детекторе, поэтому рестарт коллектора теряет только строки, записанные
  во время простоя — то же окно, что потерял бы локальный рестарт `tail -F`.

## Проверка развёртывания

Допишите пробный burst в любой отслеживаемый лог коллектора (три попадания —
одно попадание даёт score 25 при дефолтном весе `probe`, ниже дефолтного
`alert_threshold: 50`; настоящий сканер никогда не шлёт единственный запрос):

```bash
for i in 1 2 3; do
  echo '203.0.113.77 - - [04/Jul/2026:10:00:00 +0000] "GET /wp-login.php HTTP/1.1" 200 512 "-" "curl/7.88" "203.0.113.77"' >> /var/log/nginx/access.log
  sleep 0.5
done
```

Через считанные секунды вердикт должен появиться в конце вашей цепочки —
blocklist-файл респондера, address-list роутера, индекс SIEM. Если нет:
проверьте лог приёмника на WARN о неизвестной очереди (несовпадение имени) и
логи обоих узлов на строки `[TRANSPORT]`, подтверждающие QUIC-сессию.
