# Розподілена обробка подій безпеки

> 🌐 [English](DISTRIBUTED.md) | [По-русски](DISTRIBUTED.ru.md)

Один бінарник ArxSentinel. Будь-яка кількість вузлів. Збирайте події безпеки
там, куди приходить трафік, скоруйте там, де є обчислювальні ресурси,
застосовуйте заходи там, де це найболючіше для атакувальника — через наскрізно
зашифровану, взаємно автентифіковану event-мережу, вбудовану просто в рушій.
Без Redis, без Kafka, без log shipper'а, без VPN, без центрального сервера.

Цей посібник для операторів: що таке розподілений pipeline, як влаштовані
його частини, і п'ять типових інфраструктур, які можна скопіювати вже
сьогодні. Кожна топологія тут перевіряється в CI справжніми
мультиконтейнерними тестами
([`tests/integration/distributed-ncs/`](../tests/integration/distributed-ncs/README.md)) —
діаграми не «плани на майбутнє».

## Ідея за 60 секунд

В ArxSentinel завжди була внутрішня шина подій — **Named Channel Switch
(NCS)**: один pipeline пише події в іменовану чергу, інший pipeline (або
executor) читає їх назад. Досі черга жила всередині одного процесу.

**Distributed NCS** простягає ту саму чергу через мережу. Додайте блок
`queue: {type: transport}` до sink'а чи source — і бекендом іменованої черги
стає QUIC-з'єднання з іншим вузлом. Та сама форма конфігу, та сама семантика
pipeline, але два кінці тепер на різних машинах:

```
      ВУЗОЛ A                                      ВУЗОЛ B
 ┌────────────────┐                          ┌────────────────┐
 │ pipeline        │    черга "edge-raw"      │ pipeline        │
 │   sink ─────────┼── QUIC / TLS 1.3 ──────▶│   source        │
 │                 │    Ed25519 + TOFU        │                 │
 └────────────────┘                          └────────────────┘
```

Решта рушія — парсери, детектори, скорер, whitelist, executor'и — не знає й
не хоче знати, що стався мережевий хоп. Саме це правило дизайну перетворює
кожну топологію нижче на чисту вправу з конфігурації.

## Три ролі, один бінарник

Жодних спеціальних збірок «агент», «сервер» чи «менеджер» не існує. Кожен
вузол запускає той самий бінарник з тим самим форматом конфігу; його
**роль** — просто набір увімкнених частин pipeline:

| Роль | Що робить | Ключовий конфіг |
|------|-----------|-----------------|
| **Колектор** | Читає/приймає логи, парсить, прокидає **нескоровані** записи далі. Дешево: без tracker-стану, без роботи детекторів. Спокійно живе на Raspberry Pi чи VPS зі 128 MB. | `raw_forward: true` + transport-sink (`mode: send`) |
| **Детектор** | Приймає записи від будь-якої кількості колекторів, проганяє повний ланцюжок (8 поведінкових детекторів, WAF-правила, whitelist, скоринг), прокидає **скоровані вердикти** далі. Одна точка тюнінгу порогів для всього флоту. | transport-source (`mode: raw`, queue `mode: recv`) + transport-sink для вердиктів |
| **Респондер** | Приймає скоровані вердикти й застосовує заходи: nginx blocklist, MikroTik address-list, OpenWrt ipset, OPNsense alias, Cloudflare WAF або власний exec+JSON executor. Живе поруч із точкою застосування — облікові дані не покидають цей вузол. Ті самі плагіни-[виконавці](../README.uk.md#виконавці), що й у single-node розгортанні — «Респондер» — це просто ім'я ролі в розподіленій топології. | `executors:` з transport-джерелом (queue `mode: recv`) |

Ролі вільно комбінуються: вузол може детектувати **і** відповідати, збирати
**і** детектувати локально, прокидаючи лише high-severity вердикти, і так
далі. Деплой на 2 вузли та деплой на 20 вузлів будуються з тих самих трьох
кубиків.

## Що летить мережею

Два формати корисного навантаження, обираються на кожну чергу:

**Сирі записи** (`raw_forward: true` + `format: raw-line` на sink'у, що
відправляє, `mode: raw` на source, що приймає). Колектор парсить рядок у
структурований запис (IP, метод, шлях, статус, UA, timestamp), але **не**
скорує його. Вузол-детектор скорує його рівно так, ніби рядок було прочитано
з локального файлу. Застосовуйте, коли потрібна централізована детекція з
однією спільною політикою скорингу та спільним per-IP станом.

**Скоровані вердикти** (payload `sentinel-threat` за замовчуванням — без
додаткових прапорців). Повний ThreatEvent: IP, score, рівень, які детектори
спрацювали, людиночитна причина. Застосовуйте, коли детекція вже відбулася й
треба лише доставити вердикт туди, де живе enforcement (або сховище, або
SIEM).

Типовий деплой використовує обидва: сирі записи течуть усередину з
периметра, скоровані вердикти — назовні до респондерів.

## Модель безпеки транспорту

Мережа побудована на `arx-core/pkg/transport`:

- **QUIC поверх UDP** — один порт на вузол (за замовчуванням `4097`),
  мультиплексовані стріми, автоматичний reconnect з експоненційним backoff.
  Переживає нестабільні лінки.
- **Завжди TLS 1.3** — plaintext-режиму, який можна було б випадково
  увімкнути, не існує.
- **Ed25519-ідентичність вузла** — кожен вузол генерує ключову пару при
  першому старті (`transport.identity`). Без CA, без календаря закінчення
  сертифікатів.
- **Загальномережевий секрет допуску** (`transport.pairing_secret`) —
  реальний бар'єр проти чужинців: невідомий вузол повинен довести знання
  цього спільного, переданого поза протоколом секрету, перш ніж йому взагалі
  почнуть довіряти. Без нього сам лише TOFU відповідає тільки на питання
  «той самий ключ, що вчора» — але нічого не каже про те, хто взагалі
  дозволив цьому ключу приєднатися. Те саме значення — на кожному вузлі
  мережі.
- **TOFU-пінінг + самовідновлювана ротація** (`transport.known_nodes`) —
  після допуску fingerprint піра фіксується; окремий, незалежний секрет
  потім автоматично ротується після кожної сесії (без дій оператора) —
  так застаріла витеклая копія конфігу з часом перестає збігатися. Для ще
  суворішої гарантії поверх загальномережевого секрету — закріпіть очікуваний
  fingerprint заздалегідь у конфігу (`peers[].fingerprint: "sha256:..."`) —
  перевіряється раніше, ніж секрет допуску чи TOFU взагалі вступають у дію.
- **Взаємна автентифікація** — обидві сторони доводять володіння ключем через
  підписаний challenge до того, як потече хоч одна подія. Чужинець, який
  знайшов ваш UDP-порт без загальномережевого `pairing_secret`, не отримує
  нічого.

Чим мережа **не** є: брокером повідомлень з гарантіями доставки. Якщо пір
недоступний, кадри для нього відкидаються й рахуються (видно в логах і
drop-лічильниках) — та сама семантика «втрата при переповненні», що й у
in-memory черги. Для буферизації з переживанням рестарту — комбінуйте з
bbolt-чергою на стороні, що приймає
(див. `arx-core/pkg/transport/OPERATIONS.md`).

## Поверхня конфігурації

Все живе в тому самому YAML, який ви вже знаєте. Повний довідник:
[`cookbook/config.reference.yaml`](../cookbook/config.reference.yaml).

```yaml
# 1. Вмикаємо мережу на кожному вузлі-учаснику — pairing_secret однаковий
#    всюди, включно з вузлами без власних peers: (лише-приймаючий вузол
#    все одно звіряє свій секрет із вхідними з'єднаннями).
transport:
  enabled: true
  identity: /etc/arxsentinel/node.key        # генерується при першому старті
  known_nodes: /etc/arxsentinel/known-nodes  # сховище TOFU-пінів + ротований секрет
  listen: "0.0.0.0:4097"                     # QUIC/UDP
  pairing_secret: "..."                      # загальномережевий, переданий поза протоколом
  peers:                                     # лише вихідні цілі набору;
    - host: "detector.example.net:4097"      # вхідні з'єднання приймаються
      fingerprint: ""                        # і TOFU-піняться в будь-якому разі

# 2. Сторона, що відправляє — будь-який sentinel-threat sink може вказувати на піра
outputs:
  - type: sentinel-threat
    name: edge-raw            # ім'я черги — має точно збігатися з приймачем
    format: raw-line          # лише для сирих записів; прибрати для вердиктів
    queue:
      type: transport
      mode: send
      peer: "detector.example.net:4097"

# 3. Сторона, що приймає — sentinel source або джерело executor'а
inputs:
  - type: sentinel
    addr: ncs://edge-raw      # те саме ім'я черги
    mode: raw                 # декодувати сирі записи; прибрати для вердиктів
    queue:
      type: transport
      mode: recv
```

`arxsentinel validate --config ...` статично перевіряє проводку на кожному
вузлі: transport-черги вимагають `transport.enabled`, send-черги вимагають
відомого піра, а крос-вузлові черги звільнені від локальних перевірок
reader/writer.

## Порівняння з альтернативами

Розподілений захист на основі логів — не нова концепція: модель
agent/LAPI/bouncer у CrowdSec та модель agent/manager у Wazuh існують і
працюють. Відрізняється тут *форма* архітектури:

| | CrowdSec | Wazuh / OSSEC | ArxSentinel |
|---|---|---|---|
| **Топологія** | Hub-and-spoke: центральний LAPI (HTTP REST + обов'язкова БД) | Agent → manager (повна платформа: manager, indexer, dashboard) | Симетричний peer mesh — без центрального сервера, без БД |
| **Компоненти** | Агент + LAPI + окремі бінарники-баунсери на кожну точку enforcement | Manager-стек + агенти | Один бінарник ~12 MB; роль (колектор / детектор / респондер) — це просто YAML |
| **Що летить мережею** | Лише алерти й рішення — для централізації детекції сирі логи треба везти окремим shipper'ом (syslog, vector) | Події агентів на manager | Сирі розпарсені записи **і** скоровані вердикти — через один вбудований транспорт |
| **Модель доставки** | Pull: баунсери опитують LAPI за рішеннями | Push: agent → manager | Push по QUIC-mesh, автоматичний redial |
| **Автентифікація** | API-ключі / TLS-сертифікати | Pre-shared keys | Ed25519-ідентичність вузла + TOFU-пінінг, взаємна — як SSH |
| **Footprint на вузол** | Агент + баунсер(и); LAPI-вузлу потрібна БД | Manager вимірюється гігабайтами RAM | ~12 MB статичний бінарник всюди, включно з arm/v7 та riscv64 |

Обидві альтернативи — міцні проєкти зі своїми сильними сторонами (зокрема,
community-блоклісти CrowdSec тут еквівалента не мають). Твердження цього
посібника вужче й точніше: **жоден інший інструмент у цьому класі не
постачає peer-to-peer мережу подій безпеки всередині самого двигуна** — той
самий бінарник на кожному вузлі, без ієрархії агент-сервер, без окремих
компонентів enforcement, і з прокидом сирих записів на віддалений детектор
через власний транспорт двигуна — чого не пропонує жоден із перелічених.

## Топологія 1 — Два вузли: збираємо тут, детектуємо там

Мінімальний розподілений сетап і базовий патерн для всього іншого.
Веб-сервер тримає крихітний колектор поруч зі своїми логами; вся логіка
детекції, тюнінг і стан живуть на другій машині.

```
   веб-сервер (VPS, 12 MB на колектор)              машина детекції
 ┌──────────────────────────────┐            ┌──────────────────────────────┐
 │ nginx → access.log            │            │                                │
 │   │ tail                      │   QUIC     │  sentinel source (mode: raw)   │
 │   ▼                           │  ───────▶  │    │                           │
 │ pipeline колектора            │ "edge-raw" │    ▼                           │
 │  лише парсинг — raw_forward   │            │  8 детекторів · WAF · whitelist│
 │  sink: transport, mode: send  │            │  скорер → threats.log / бани   │
 └──────────────────────────────┘            └──────────────────────────────┘
```

**Коли**: не хочете CPU/стан детекторів на веб-сервері; хочете тюнити скоринг
в одному місці; веб-машина має залишатися мінімальною.

**Рецепт**: [`cookbook/distributed-ncs/`](../cookbook/distributed-ncs/README.md)
(`collector.yaml` + `detector.yaml`, повний walkthrough всередині).

## Топологія 2 — Edge-флот: багато колекторів, один мозок

Агрегація: будь-яка кількість колекторів прокидає на **те саме ім'я черги**;
єдина реєстрація на детекторі приймає всіх. Одна політика скорингу, один
whitelist, один спільний per-IP стан — атакувальник, що промацує три ваші
сервіси, накопичує один сумарний score і перетинає поріг бану раніше, ніж
його впіймав би будь-який сервіс поодинці.

```
 ┌────────────────┐
 │ nginx edge      │──┐
 └────────────────┘  │
 ┌────────────────┐  │  черга "edge-raw"    ┌──────────────┐   черга          ┌──────────────┐
 │ API gateway     │──┼───────────────────▶│   детектор    │─────────────────▶│  респондер    │
 └────────────────┘  │  (одне ім'я з усіх  │ повний ланцюжок│ "scored-events" │ nginx executor │
 ┌────────────────┐  │   колекторів)       │ спільний стан │                  │ blocklist-файл │
 │ auth service    │──┘                     └──────────────┘                  └──────────────┘
 └────────────────┘
```

**Коли**: різнорідні джерела (веб-шар + API + auth), кореляція атак між
сервісами, «додати колектор» має бути 30 рядками YAML, а не інфраструктурним
проєктом.

**Рецепт**: [`cookbook/distributed-ncs/aggregation/`](../cookbook/distributed-ncs/aggregation/README.md).
**CI-доказ**: `docker-compose.aggregation.yml` — 5 справжніх контейнерів, на
кожному PR.

## Топологія 3 — Змішана маршрутизація: різні джерела — різні заходи

Один процес-детектор, кілька pipeline — кожен приймає трафік свого джерела й
прокидає вердикти своєму респондеру. Атаки на веб-шар баняться на
веб-рівні; атаки на auth/мережу — на роутері. Рішення про маршрут — це те,
через який pipeline трафік увійшов; ухвалюється на етапі конфігу, нуль
per-event логіки маршрутизації.

```
 ┌────────────────┐  "edge-web"         ┌──────────────────┐  "scored-web"     ┌─────────────────┐
 │ collector-web  │────────────────────▶│ pipeline "web"   │──────────────────▶│ nginx-респондер │
 └────────────────┘                     │                  │                   │ blocklist-файл  │
 ┌────────────────┐  "edge-auth"        │     детектор     │                   └─────────────────┘
 │ collector-auth │────────────────────▶│ pipeline "auth"  │  "scored-auth"    ┌──────────────┐
 └────────────────┘                     │                  │──────────────────▶│ MikroTik     │
                                        └──────────────────┘                   │ address-list │
                                                                               └──────────────┘
```

**Коли**: різним класам трафіку потрібні різні механізми enforcement або
різні політики TTL/severity, але детекція має залишитися на одній машині.

**Рецепт**: [`cookbook/distributed-ncs/mixed-routing/`](../cookbook/distributed-ncs/mixed-routing/README.md).
**CI-доказ**: `docker-compose.mixed-routing.yml` — включає справжній мок
RouterOS API і крос-перевірки, що вердикти не «протікають» між маршрутами.

## Топологія 4 — Хоумлаб: Pi-колектори, NAS-мозок, бан на роутері

Весь флот коштує вам ~40 MB RAM сумарно. Колектори запускаються всюди, де
пишеться лог — включно з arm/v7 та riscv64-платами. Мозок живе на тому, що
завжди увімкнене (NAS, міні-ПК). Enforcement відбувається на вашому
MikroTik — атакувальники відкидаються на межі мережі, не діставшись жодного
сервісу.

```
 ┌────────────────────────────┐
 │ Raspberry Pi · логи проксі │──┐
 └────────────────────────────┘  │              ┌───────────────────────┐               ┌─────────────────────┐
 ┌────────────────────────────┐  │  "edge-raw"  │    NAS / міні-ПК      │  "scored"     │ MikroTik executor   │
 │ VPS · публічний веб        │──┼─────────────▶│ детектор: 8 ланцюжків │──────────────▶│ (теж на NAS —       │
 └────────────────────────────┘  │              │ + WAF + whitelist     │               │ креди RouterOS      │
 ┌────────────────────────────┐  │              └───────────────────────┘               │ не покидають дім)   │
 │ NAS · локальні сервіси     │──┘                                                      └─────────────────────┘
 └────────────────────────────┘                                                                    ▼
                                                                                       /ip/firewall/address-list
                                                                                           → drop на роутері
```

**Коли**: кілька машин, один оператор і нуль бажання тримати вдома Kafka.
Транспорт сам собі VPN — плече від VPS вже зашифроване TLS 1.3 і запінене,
тож публічному колектору не потрібен тунель додому. З інтернету має бути
доступний лише UDP-порт детектора (один порт-форвард на роутері).

**З чого почати**: рецепт Топології 2 з одним колектором на машину; замініть
executor респондера на `type: mikrotik`
(конфіг executor'а — у [`cookbook/mikrotik/`](../cookbook/mikrotik/)).

## Топологія 5 — Корпоративна: edge-детекція + потік у SIEM

Винесіть детекцію туди, куди приходить трафік (філії, edge-PoP,
DMZ-сегменти), і надсилайте в корпоративний стек **структуровані, попередньо
скоровані події** — а не гігабайти сирих логів. Кожен вузол уміє видавати
обидва формати одночасно:

- **Сирі нормалізовані записи** — кожен розпарсений запит як структурований
  JSON (`format: raw-line` або локальний `json` file/stdout-sink): повний
  потік для threat hunting, форензики та моделей, яким потрібно все.
- **Скоровані вердикти** — лише те, що перетнуло поріг, зі score, списком
  детекторів і причиною: alert-grade потік, який ваш SOC реально читає, за
  частку обсягу інжесту.

```
 ┌──────────────────┐  "edge-*" · QUIC              ┌──────────────────────────┐             ┌──────────────────┐
 │ колектор · філія │──────────────────────────────▶│    кластер детекції      │  exec+JSON  │ SIEM / data lake │
 └──────────────────┘                               │   (per-site або центр)   │────────────▶│ Splunk · Elastic │
                                                    │ сирий JSON + score ────▶ │             │ QRadar · будь-що │
 ┌──────────────────┐                               │                          │             └──────────────────┘
 │ колектор · DMZ   │──────────────────────────────▶│ скоровані вердикти ────▶ │             ┌───────────────────┐
 └──────────────────┘                               │                          │────────────▶│ enforcement       │
                                                    └──────────────────────────┘  QUIC-мережа│ CF WAF · MikroTik │
                                                                                             │ nginx · exec+JSON │
                                                                                             └───────────────────┘
```

Ключові властивості для корпоративної оцінки:

- **Контроль вартості інжесту.** Префільтрація на edge означає, що рахунок за
  SIEM визначається *загрозами*, а не *трафіком*. Перемкніть один sink на
  `raw-line`, коли розслідуванню потрібен повний потік — per pipeline, per
  site.
- **Без вхідних дірок.** Колектори з'єднуються **назовні** до детектора;
  файрволам філій не потрібно жодного вхідного правила. Облікові дані
  enforcement (токени Cloudflare, паролі RouterOS) живуть лише на
  вузлах-респондерах.
- **Єдиний агент.** Той самий статичний бінарник ~12 MB на кожному вузлі —
  amd64, arm64, arm/v7, riscv64, i386, Linux і FreeBSD — один пакет для
  сертифікації, один формат конфігу для рев'ю.
- **Дружньо до аудиту.** `arxsentinel validate` доводить проводку офлайн;
  кожна топологія цього посібника проганяється CI на справжніх контейнерах
  при кожному merge.

**Шляхи в SIEM сьогодні**: нативні sink'и **Splunk HEC**, **Loki** та
**Datadog** (готові рецепти — у [`cookbook/observability/`](../cookbook/observability/))
покривають три найпоширеніші корпоративні приймачі з коробки. Для всього
іншого — Kafka, S3, власний HEC-аплоадер, внутрішня шина — підійде
універсальний `exec+JSON` sink (будь-який скрипт чи бінарник), `file` sink у
форматі JSON (підхоплюється будь-яким наявним форвардером) і `stdout` JSON
для контейнерних лог-пайплайнів.

## Експлуатація

- **Порядок запуску**: для коректності не важливий — додзвін повторюється з
  backoff (1s → 30s, з джитером). Запуск приймачів першими лише економить
  перший backoff-удар.
- **Імена черг мають збігатися точно** на обох кінцях (`name:` на sink'у,
  `ncs://<ім'я>` на source). Розбіжність — не помилка старту (ім'я стає
  значущим, лише коли обидва вузли підняті) — вона проявляється як зростаючий
  drop-лічильник і rate-limited WARN на приймачі. Процедура діагностики:
  `arx-core/pkg/transport/OPERATIONS.md` §4.
- **Файрвол**: один UDP-порт на вузол (за замовчуванням `4097`), лише в
  напрямку набору колектор→детектор / детектор→респондер.
- **Ротація ключа / компрометація вузла**: видаліть рядок вузла з
  `known_nodes` кожного піра, видаліть файл `identity` вузла, перезапустіть —
  свіжа ключова пара згенерується й перепіниться при наступному контакті
  (їй знову доведеться пройти гейт `pairing_secret`, як будь-якому новому
  вузлу). Заздалегідь прописані fingerprints у конфігу теж треба оновити.
- **Ротація секрету допуску — автоматична** — жодних дій оператора у
  штатному режимі не потрібно, вона ротується сама після кожної успішної
  сесії. Якщо ви підозрюєте витік самого значення `pairing_secret` (не
  ідентичності одного вузла, а загальномережевого секрету) — ротуйте його
  явно: згенеруйте новий, оновіть на кожному вузлі, перезапустіть усі разом
  (вузол на старому значенні не пройде допуск із вузлами вже на новому).
- **Семантика відмов**: недоступний пір відкидає (і рахує) кадри, надіслані
  йому; перепідключення автоматичне. Стан детекції живе на детекторі, тому
  рестарт колектора втрачає лише рядки, записані під час простою — те саме
  вікно, що втратив би локальний рестарт `tail -F`.

## Перевірка розгортання

Допишіть пробний burst у будь-який відстежуваний лог колектора (три
влучання — одне влучання дає score 25 при дефолтній вазі `probe`, нижче
дефолтного `alert_threshold: 50`; справжній сканер ніколи не шле єдиний
запит):

```bash
for i in 1 2 3; do
  echo '203.0.113.77 - - [04/Jul/2026:10:00:00 +0000] "GET /wp-login.php HTTP/1.1" 200 512 "-" "curl/7.88" "203.0.113.77"' >> /var/log/nginx/access.log
  sleep 0.5
done
```

За лічені секунди вердикт має з'явитися в кінці вашого ланцюжка —
blocklist-файл респондера, address-list роутера, індекс SIEM. Якщо ні:
перевірте лог приймача на WARN про невідому чергу (розбіжність імені) і логи
обох вузлів на рядки `[TRANSPORT]`, що підтверджують QUIC-сесію.
